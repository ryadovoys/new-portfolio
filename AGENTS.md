# Portfolio Agent Guide

This file is the project-level operating guide for agents working in:
`/Users/sergeyryadovoy/Work/Portfolio`

## Purpose

- This project is Sergey's portfolio site and content system.
- Main job here is high-quality content + presentation updates.
- Treat this as independent from other `Work/` projects unless user explicitly links them.

## What this project contains

- `data/cards.json` - source of truth for portfolio cards
- `data/content-rules.md` - writing rules by card tag (Personal/Project/Skill/Experience/Experiment)
- `assets/` - media + folder-based project assets
- `index.html`, `css/`, `js/` - front-end implementation
- `scripts/build.js` - production build pipeline
- `dist/` - generated output (do not hand-edit)
- `.compare/` - temporary compare files for content review
- `.agent/AGENTS.md` - deeper product context and history

## Mandatory startup protocol (inside this project)

1. Read `AGENTS.md` (this file).
2. Read `.agent/AGENTS.md` for additional context.
3. If request is copy/content related, read `data/content-rules.md` before editing.
4. If request targets cards, read `data/cards.json` before proposing changes.

## Scope boundaries

- Work only inside this project unless user asks otherwise.
- Do not pull content from unrelated workspace folders by default.
- If cross-project input is needed (e.g., job application support), ask or follow explicit user request.

## Content-first workflow

For card text updates, use this flow:

1. Identify targeted cards by title/tag.
2. Propose before/after text.
3. Use compare workflow (`.compare/`) when user asks to compare.
4. Apply edits only after user approval.

## Compare workflow

When user asks to compare:

- Create temp file in `.compare/compare-<topic>-<timestamp>.md`
- Start with original content in `## Working copy`
- Edit text in place (same file)
- Show diff summary and file path
- Apply approved text to destination file
- Delete temp file by default unless user asks to keep

## Card writing guidance (quick summary)

Use `data/content-rules.md` as source of truth. Key reminders:

- Keep language direct and specific.
- Keep claims factual and defensible.
- Avoid resume-like tone on portfolio cards.

By tag:

- `Project`: describe what the project is first, then your role, then scope/output.
- `Skill`: show practical capability and where/how it is used.
- `Experience`: show operating pattern across contexts, not one isolated project.
- `Experiment`: frame as exploration/hypothesis, not scaled-product claim.
- `Personal`: establish positioning in one clear read.

Wide cards:

- Prefer richer narrative when real detail exists.
- Preserve useful scope details (partners, systems, outputs) instead of over-compressing.

## Front-end and build notes

- Install deps: `npm install`
- Run local server: `npm run dev`
- Build static output: `npm run build`

Important:

- `dist/` is generated by build; do not manually maintain it.
- If source files change (`data/`, `assets/`, `css/`, `js/`, `index.html`), rebuild when needed.

## Editing rules

- Keep paths and links valid (`card.folder`, `card.media`, `card.link`).
- Maintain JSON validity in `data/cards.json`.
- Keep naming/style consistent with existing cards.
- Avoid unnecessary rewrites outside requested scope.

## Safety

- Do not edit `node_modules/`.
- Do not delete project assets/folders unless user explicitly asks.
- Do not run destructive workspace-level commands.

## Done criteria

Task is complete when:

- Requested cards/files were updated in project scope only.
- User can review clear before/after changes.
- Build-related steps were run if needed for verification.
- Temporary compare files were cleaned up (unless user asked to keep them).

## If unsure

- Prefer small, reversible edits.
- Ask one focused question only if ambiguity materially changes output.
